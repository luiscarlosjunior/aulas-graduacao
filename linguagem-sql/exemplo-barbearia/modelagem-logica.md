# Modelagem Lógica - Sistema Barbearia

## 📋 Visão Geral

A **modelagem lógica** traduz o modelo conceitual para estruturas que podem ser implementadas em um Sistema de Gerenciamento de Banco de Dados (SGBD) relacional, especificamente Oracle Database. Neste nível, definimos tabelas, chaves, tipos de dados e constraints.

## 🏗️ Estrutura das Tabelas

### 📄 CLIENTES

```sql
CLIENTES (
    id                NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome              VARCHAR2(120) NOT NULL,
    telefone          VARCHAR2(25),
    email             VARCHAR2(120),
    data_cadastro     DATE DEFAULT SYSDATE,
    ativo             CHAR(1) DEFAULT 'S' CHECK (ativo IN ('S', 'N')),
    
    -- Constraints
    CONSTRAINT uk_clientes_email UNIQUE (email),
    CONSTRAINT chk_clientes_nome CHECK (LENGTH(nome) >= 2),
    CONSTRAINT chk_clientes_email CHECK (email LIKE '%_@_%._%')
)
```

**Justificativas das Escolhas**:
- **id**: `NUMBER IDENTITY` para chave primária auto-incrementável
- **nome**: `VARCHAR2(120)` permite nomes completos longos
- **telefone**: `VARCHAR2(25)` suporta formatação como "+55 (11) 99999-9999"
- **email**: `VARCHAR2(120)` para emails modernos longos
- **ativo**: `CHAR(1)` para flag simples S/N (mais eficiente que BOOLEAN)

### 👨‍💼 BARBEIROS

```sql
BARBEIROS (
    id                NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome              VARCHAR2(120) NOT NULL,
    telefone          VARCHAR2(25),
    especialidade     VARCHAR2(100),
    data_admissao     DATE DEFAULT SYSDATE,
    ativo             CHAR(1) DEFAULT 'S' CHECK (ativo IN ('S', 'N')),
    
    -- Constraints
    CONSTRAINT chk_barbeiros_nome CHECK (LENGTH(nome) >= 2)
)
```

**Justificativas das Escolhas**:
- **especialidade**: `VARCHAR2(100)` para descrições como "Cortes Clássicos e Modernos"
- **data_admissao**: `DATE` para controle de tempo de casa do funcionário
- Mesma estrutura de **id** e **ativo** para consistência

### 🎨 SERVICOS

```sql
SERVICOS (
    id                NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome              VARCHAR2(100) NOT NULL,
    descricao         VARCHAR2(500),
    duracao_min       NUMBER NOT NULL,
    preco             NUMBER(8,2) DEFAULT 0,
    ativo             CHAR(1) DEFAULT 'S' CHECK (ativo IN ('S', 'N')),
    
    -- Constraints
    CONSTRAINT uk_servicos_nome UNIQUE (nome),
    CONSTRAINT chk_servicos_duracao CHECK (duracao_min > 0 AND duracao_min <= 480),
    CONSTRAINT chk_servicos_preco CHECK (preco >= 0),
    CONSTRAINT chk_servicos_nome CHECK (LENGTH(nome) >= 3)
)
```

**Justificativas das Escolhas**:
- **descricao**: `VARCHAR2(500)` para descrições detalhadas dos serviços
- **duracao_min**: `NUMBER` simples, com CHECK para máximo 8 horas
- **preco**: `NUMBER(8,2)` permite preços até 999.999,99 com centavos
- **nome único**: Evita duplicação de serviços

### 📅 AGENDAMENTOS

```sql
AGENDAMENTOS (
    id                NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    cliente_id        NUMBER NOT NULL,
    barbeiro_id       NUMBER NOT NULL,
    inicio            TIMESTAMP NOT NULL,
    fim               TIMESTAMP,
    status            VARCHAR2(15) DEFAULT 'MARCADO' NOT NULL,
    observacoes       VARCHAR2(500),
    valor_total       NUMBER(8,2) DEFAULT 0,
    data_criacao      TIMESTAMP DEFAULT SYSTIMESTAMP,
    
    -- Foreign Keys
    CONSTRAINT fk_ag_cli FOREIGN KEY (cliente_id) REFERENCES clientes(id) ON DELETE CASCADE,
    CONSTRAINT fk_ag_bar FOREIGN KEY (barbeiro_id) REFERENCES barbeiros(id),
    
    -- Constraints
    CONSTRAINT chk_ag_status CHECK (status IN ('MARCADO','CANCELADO','CONCLUIDO','EM_ANDAMENTO')),
    CONSTRAINT chk_ag_datas CHECK (fim IS NULL OR fim > inicio),
    CONSTRAINT chk_ag_valor CHECK (valor_total >= 0),
    CONSTRAINT chk_ag_inicio CHECK (inicio > SYSTIMESTAMP - INTERVAL '1' DAY)
)
```

**Justificativas das Escolhas**:
- **TIMESTAMP**: Mais preciso que DATE para agendamentos
- **status**: `VARCHAR2(15)` para legibilidade (melhor que códigos numéricos)
- **ON DELETE CASCADE**: Se cliente for excluído, seus agendamentos também
- **fim NULL**: Permite agendamentos futuros sem fim definido
- **valor_total**: Calculado, mas armazenado para performance e histórico

### 🔗 AGENDAMENTO_SERVICOS (Tabela de Relacionamento N:M)

```sql
AGENDAMENTO_SERVICOS (
    agendamento_id    NUMBER NOT NULL,
    servico_id        NUMBER NOT NULL,
    quantidade        NUMBER DEFAULT 1 NOT NULL,
    preco_unitario    NUMBER(8,2),
    observacoes       VARCHAR2(200),
    
    -- Chave Primária Composta
    PRIMARY KEY (agendamento_id, servico_id),
    
    -- Foreign Keys
    CONSTRAINT fk_as_ag FOREIGN KEY (agendamento_id) REFERENCES agendamentos(id) ON DELETE CASCADE,
    CONSTRAINT fk_as_sv FOREIGN KEY (servico_id) REFERENCES servicos(id),
    
    -- Constraints
    CONSTRAINT chk_as_qtd CHECK (quantidade > 0),
    CONSTRAINT chk_as_preco CHECK (preco_unitario IS NULL OR preco_unitario >= 0)
)
```

**Justificativas das Escolhas**:
- **Chave primária composta**: Evita duplicação do mesmo serviço no agendamento
- **quantidade**: Permite repetir serviços (ex: 2 reflexos)
- **preco_unitario**: Preço na data do agendamento (histórico)
- **ON DELETE CASCADE**: Remove serviços se agendamento for excluído

## 🔑 Estratégia de Chaves

### Chaves Primárias

**Padronização Adotada**:
- Todas as entidades principais usam **chaves surrogate**
- Tipo `NUMBER` com `IDENTITY` para auto-incremento
- Nomenclatura padrão: `id`

**Vantagens**:
- Performance otimizada (números inteiros)
- Imutabilidade (não mudam mesmo se dados de negócio mudarem)
- Simplicidade nas junções
- Independência dos dados de negócio

### Chaves Estrangeiras

```sql
-- Relacionamentos implementados
AGENDAMENTOS.cliente_id   → CLIENTES.id
AGENDAMENTOS.barbeiro_id  → BARBEIROS.id
AGENDAMENTO_SERVICOS.agendamento_id → AGENDAMENTOS.id
AGENDAMENTO_SERVICOS.servico_id → SERVICOS.id
```

**Políticas de Integridade**:
- **CASCADE DELETE**: Em relacionamentos de composição (agendamento → serviços)
- **RESTRICT DELETE**: Em relacionamentos de referência (barbeiro → agendamentos)

### Chaves Únicas (Alternativas)

```sql
-- Chaves de negócio únicas
CLIENTES.email          -- Login/identificação
SERVICOS.nome          -- Evita serviços duplicados
```

## 📊 Tipos de Dados e Domínios

### Escolhas de Tipos Oracle

#### Textos
- **VARCHAR2**: Usado para todos os campos texto variável
- **CHAR(1)**: Para flags simples (ativo S/N)
- Evitamos `NVARCHAR2` pois não há necessidade de Unicode especial

#### Números
- **NUMBER**: Tipo genérico do Oracle para inteiros
- **NUMBER(8,2)**: Para valores monetários (até 999.999,99)
- Precisão definida para evitar problemas de arredondamento

#### Datas e Tempos
- **DATE**: Para datas simples (cadastro, admissão)
- **TIMESTAMP**: Para agendamentos (precisão de segundos)
- **SYSTIMESTAMP**: Para auditoria (inclui timezone)

#### Domínios Definidos

```sql
-- Status de agendamento
DOMAIN status_agendamento AS VARCHAR2(15)
CHECK (VALUE IN ('MARCADO','CANCELADO','CONCLUIDO','EM_ANDAMENTO'))

-- Flag ativo/inativo
DOMAIN flag_ativo AS CHAR(1)
CHECK (VALUE IN ('S','N'))

-- Duração de serviços (em minutos)
DOMAIN duracao_servico AS NUMBER
CHECK (VALUE > 0 AND VALUE <= 480)
```

## 🔄 Relacionamentos no Modelo Lógico

### Implementação 1:N

```sql
-- CLIENTE → AGENDAMENTOS
AGENDAMENTOS.cliente_id → CLIENTES.id

-- BARBEIRO → AGENDAMENTOS  
AGENDAMENTOS.barbeiro_id → BARBEIROS.id
```

**Características**:
- Chave estrangeira no lado "N"
- Constraint de integridade referencial
- Permite navegação eficiente

### Implementação N:M

```sql
-- AGENDAMENTO ↔ SERVICO
Tabela intermediária: AGENDAMENTO_SERVICOS
- agendamento_id → AGENDAMENTOS.id
- servico_id → SERVICOS.id
- Atributos do relacionamento: quantidade, preco_unitario, observacoes
```

**Características**:
- Chave primária composta
- Duas chaves estrangeiras
- Atributos próprios do relacionamento

## 🛠️ Normalização

### Análise das Formas Normais

#### 1ª Forma Normal (1FN) ✅
- **Atendida**: Todos os atributos são atômicos
- **Exemplo**: Nome completo em um campo, sem separar nome/sobrenome
- **Justificativa**: Para este domínio, nome completo é suficiente

#### 2ª Forma Normal (2FN) ✅
- **Atendida**: Não há dependências parciais
- **Verificação**: Tabela AGENDAMENTO_SERVICOS tem chave composta (agendamento_id, servico_id)
  - `quantidade` depende de ambas as partes da chave ✅
  - `preco_unitario` depende de ambas as partes da chave ✅
  - `observacoes` depende de ambas as partes da chave ✅

#### 3ª Forma Normal (3FN) ✅
- **Atendida**: Não há dependências transitivas
- **Análise**: 
  - CLIENTES: nome, telefone, email dependem diretamente de id ✅
  - AGENDAMENTOS: valor_total poderia ser calculado, mas mantido para performance ✅
  - Todos os demais atributos dependem diretamente da chave primária

### Decisões de Desnormalização

#### Valor Total no Agendamento
```sql
AGENDAMENTOS.valor_total -- Desnormalizado para performance
```

**Justificativa**:
- **Performance**: Evita cálculo em tempo real
- **Histórico**: Preserva valor na data do agendamento
- **Relatórios**: Consultas mais rápidas
- **Trade-off**: Pequena redundância vs. grande ganho de performance

## 🔧 Triggers e Automações

### Triggers de Auditoria
```sql
-- Atualização automática de timestamps
CREATE OR REPLACE TRIGGER trg_agendamentos_audit
BEFORE UPDATE ON agendamentos
FOR EACH ROW
BEGIN
    :NEW.data_criacao := :OLD.data_criacao; -- Preserva data original
END;
```

### Triggers de Validação
```sql
-- Validação de agendamento apenas com entidades ativas
CREATE OR REPLACE TRIGGER trg_agendamentos_validacao
BEFORE INSERT OR UPDATE ON agendamentos
FOR EACH ROW
DECLARE
    v_cliente_ativo CHAR(1);
    v_barbeiro_ativo CHAR(1);
BEGIN
    -- Verifica se cliente está ativo
    SELECT ativo INTO v_cliente_ativo FROM clientes WHERE id = :NEW.cliente_id;
    IF v_cliente_ativo = 'N' THEN
        RAISE_APPLICATION_ERROR(-20001, 'Cliente inativo não pode fazer agendamentos');
    END IF;
    
    -- Verifica se barbeiro está ativo
    SELECT ativo INTO v_barbeiro_ativo FROM barbeiros WHERE id = :NEW.barbeiro_id;
    IF v_barbeiro_ativo = 'N' THEN
        RAISE_APPLICATION_ERROR(-20002, 'Agendamento não pode ser feito com barbeiro inativo');
    END IF;
END;
```

## 📊 Views Estratégicas

### View de Agendamentos Completos
```sql
CREATE VIEW vw_agendamentos_completos AS
SELECT 
    a.id,
    a.inicio,
    a.fim,
    a.status,
    c.nome AS cliente_nome,
    c.email AS cliente_email,
    b.nome AS barbeiro_nome,
    b.especialidade,
    a.valor_total,
    a.observacoes
FROM agendamentos a
JOIN clientes c ON c.id = a.cliente_id
JOIN barbeiros b ON b.id = a.barbeiro_id;
```

### View de Serviços por Agendamento
```sql
CREATE VIEW vw_agendamentos_servicos AS
SELECT 
    a.id AS agendamento_id,
    c.nome AS cliente,
    LISTAGG(s.nome, ', ') WITHIN GROUP (ORDER BY s.nome) AS servicos,
    SUM(asv.quantidade * asv.preco_unitario) AS valor_servicos
FROM agendamentos a
JOIN clientes c ON c.id = a.cliente_id
JOIN agendamento_servicos asv ON asv.agendamento_id = a.id
JOIN servicos s ON s.id = asv.servico_id
GROUP BY a.id, c.nome;
```
